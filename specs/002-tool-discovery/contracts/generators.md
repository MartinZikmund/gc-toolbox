# Contract: `GcToolkit.SourceGenerators`, Diagnostics & Navigation Hosting

**One** incremental source generator, project `GcToolkit.SourceGenerators` (`netstandard2.0` analyzer), **referenced by the app head `GcToolkit`** — exactly like `WinUIGallery.SourceGenerator`, whose single generator runs against the app (R1/R2/R13). It sees the app-head `View` types directly and the `[Tool]` ViewModels via the referenced `GcToolkit.Core` assembly's metadata, and emits everything into the app head. Decisions referenced as **R#** map to [../research.md](../research.md).

---

## A. `ToolDiscoveryGenerator` — inputs

| Input | Provider | Notes |
|---|---|---|
| `[Tool]` ViewModels (in **Core**) | `CompilationProvider` → scan `IAssemblySymbol`s for types carrying `GcToolkit.Core.Discovery.ToolAttribute` | Metadata scan, **not** `ForAttributeWithMetadataName` — the attributed types live in a referenced assembly, not the app's source. Attribute ctor args (`Id`, `Category`, `Introduced`, `Updated`, `Keywords`) are read from `AttributeData`; base type checked via the `INamedTypeSymbol.BaseType` chain. |
| `ViewBase<TVm>` views (in the **app head**) | `SyntaxProvider` (syntax) | Each concrete view → its `TVm`. Syntax-based, so these get precise diagnostic locations. |
| `.resw` files (app head) | `AdditionalTextsProvider` (`Strings/{en,cs}/Resources.resw`) | Validate `<Id>_Name` / `<Id>_Tooltip` per culture (R8). Wired via `<AdditionalFiles Include="Strings/**/Resources.resw" />`. |
| Build properties | `AnalyzerConfigOptionsProvider` | `build_property.RootNamespace`, `build_property.ProjectDir` (WinUI Gallery pattern). |

> **Incrementality**: keyed on `CompilationProvider` (coarser than `ForAttributeWithMetadataName`), but the discovery transform produces a small immutable model, so `RegisterSourceOutput` only re-emits when the discovered set actually changes. Negligible for this catalog size (R13).

## B. Outputs (emitted into the **app head**, `<auto-generated/>` header, deterministic — no timestamp, R13)

| File (`*.g.cs`) | Content |
|---|---|
| `GeneratedToolContributor.g.cs` | `internal sealed class GeneratedToolContributor : IToolContributor, ICategoryContributor` returning the discovered `ToolDescriptor`s (name/tooltip keys, dates parsed to `DateOnly`, icon key = `Id`, `GroupId` from the map, `ViewModelType = typeof(<Core tool VM>)`) and the `Category`s (from `ToolCategory` + the category→group map). |
| `GeneratedToolCatalog.g.cs` | `public static class GeneratedToolCatalog { IReadOnlyList<Type> ToolViewModelTypes; NavigationTree NavigationTree; }` — `NavigationTree` instance built from the discovered metadata. |
| `ToolDiscoveryServiceCollectionExtensions.g.cs` | `public static IServiceCollection AddDiscoveredTools(this IServiceCollection services)` — registers the contributor (as `IToolContributor` + `ICategoryContributor`) and each tool VM (transient). |
| `ViewRegistrations.g.cs` | `public static void RegisterDiscoveredViews(this NavigationService nav)` calling `RegisterView(typeof(TView), typeof(TVm))` for every `ViewBase<TVm>` view, **plus** `RegisterView(typeof(ToolHostView), typeof(TToolVm))` for each discovered tool VM (R2, R10). |

All four reference Core types (`ToolDescriptor`, `Category`, the tool VM types) and app-head types (`ToolHostView`, the `View`s) — legal because the app head references Core.

**Ordering**: deterministic — group `Order` → category `Order` → tool `Id` (ordinal), matching `CatalogService` (FR-023). Empty categories/groups omitted from `NavigationTree` (FR-024).

**Consumption** (both calls **once** in `App.RegisterServices`, replacing the placeholder + hand-written `RegisterView` block):

```csharp
services.AddDiscoveredTools();                 // generated — feeds CatalogService (unchanged)
// inside the INavigationService factory:
var nav = new NavigationService(shellProvider);
nav.RegisterDiscoveredViews();                 // generated — all view↔VM + tool VM → ToolHostView
```

`CatalogService` is unchanged — it aggregates the generated contributor like any other; manual `IToolContributor`s still work as a fallback (FR-010, FR-018).

## C. Diagnostics catalog

Category `GcToolkit.SourceGenerator`. Severity reflects R8 (honor `WarningsAsErrors=True`; everything detectable is an **Error**, icons excepted). IDs are illustrative.

| ID | Severity | Condition | Location | Message (actionable) |
|---|---|---|---|---|
| `GCTOOL001` | Error | `[Tool]` missing a required value, or `Id` not PascalCase/resource-safe | `Location.None`* | `Tool '<type>': <Id|Category|Introduced|Updated> is required / 'Id' must be a resource-safe PascalCase identifier.` |
| `GCTOOL002` | Error | `[Tool]` on a type **not** deriving `ToolViewModelBase` | `Location.None`* | `'<type>' is marked [Tool] but is not a navigable tool ViewModel (must derive ToolViewModelBase).` |
| `GCTOOL003` | Error | `Introduced`/`Updated` not a valid `yyyy-MM-dd` date | `Location.None`* | `Tool '<Id>': '<value>' is not a valid ISO date (yyyy-MM-dd).` |
| `GCTOOL004` | Error | `<Id>_Name` or `<Id>_Tooltip` missing in a required culture | the `.resw` `AdditionalText` | `Tool '<Id>': resource '<key>' not found in <culture> (Strings/<culture>/Resources.resw).` |
| `GCTOOL010` | Info | `Updated` earlier than `Introduced` (tolerated inconsistency, R9) | `Location.None`* | `Tool '<Id>': Updated (<u>) precedes Introduced (<i>); treated as introduced-only.` |

\* **Location caveat (accepted trade-off, R2)**: tool VMs live in Core but the generator runs in the app head, so `GCTOOL001/002/003/010` carry **no source location** — they identify the offending type by full name + `Id` instead. `GCTOOL004` *can* point at the `.resw` (it lives in the app head). **Not diagnostics**: missing icon bitmap → silent runtime placeholder (R7). **Duplicate `Id`** → startup `InvalidOperationException` via `CatalogService` (FR-004), not build-time.

> `GCTOOL010` is the only non-Error; under `WarningsAsErrors=True` an `Info` does not fail the build (a `Warning` would). All structural/resource problems are `Error`.

**Optional mitigation (not in the default scope)**: to recover precise source locations for `GCTOOL001/002/003`, the same `GcToolkit.SourceGenerators` assembly could additionally be referenced by `GcToolkit.Core` *analyzer-only* as a small `DiagnosticAnalyzer` validation pass (which sees Core's syntax). This keeps one project/DLL while restoring pinpointed errors. Deferred unless diagnostic precision proves painful.

## D. Navigation-hosting contract (stub tools share `ToolHostView`) — R10

The trickiest seam: ~10 distinct `[Tool]` VMs, one shared host view, view-model-first navigation, **no per-tool pages** (out of scope; the generator must not emit XAML — FR-013).

**Contract**:
1. Every stub tool VM derives `ToolViewModelBase`, which (on activation) resolves its descriptor by `ToolId`, sets `ToolName`/`Tooltip`/`PageTitle`, records the open in `IRecentsService` (FR-020), and exposes the favorite toggle.
2. Opening a tool is view-model-first: `INavigationService.Navigate<TToolViewModel>()`.
3. The generator registers **every** discovered tool VM → `typeof(ToolHostView)`.
4. `ToolHostView` is adapted so a **single** view hosts the **concrete** navigated tool VM: navigation conveys the target VM type, the view resolves that VM from DI, binds it as `DataContext`, and drives the `ViewModelBase` lifecycle (instead of the fixed `ViewBase<ToolHostViewModel>` resolution). The exact wiring (navigate to `ToolHostView` with the VM `Type` as parameter, vs. a small `NavigationService` branch when the resolved view is the shared host) is an implementation detail finalized in design; the **contract** is: `Navigate<TToolViewModel>()` opens `TToolViewModel` rendered by `ToolHostView`, recording recents identically whether opened from the pane or the Catalog page (FR-020).

**Why not per-tool views**: per-tool pages are out of scope, and the generator must not emit UI (FR-013). A single shared `ToolHostViewModel` target (today's model) can't carry per-tool `[Tool]` attributes the spec requires on each tool's own VM (FR-009).

## E. Generator project recipe (mirrors `WinUIGallery.SourceGenerator.csproj`, R13)

```xml
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <TargetFramework>netstandard2.0</TargetFramework>
    <LangVersion>latest</LangVersion>
    <Nullable>enable</Nullable>
    <IncludeBuildOutput>false</IncludeBuildOutput>
    <IsRoslynComponent>true</IsRoslynComponent>
    <EnforceExtendedAnalyzerRules>true</EnforceExtendedAnalyzerRules>
  </PropertyGroup>
  <ItemGroup>
    <PackageReference Include="Microsoft.CodeAnalysis.Analyzers" PrivateAssets="all" />
    <PackageReference Include="Microsoft.CodeAnalysis.CSharp" />   <!-- 4.x, version via Directory.Packages.props (CPM) -->
  </ItemGroup>
</Project>
```

Referenced by the **app head** (`src/GcToolkit/GcToolkit.csproj`):

```xml
<ProjectReference Include="..\GcToolkit.SourceGenerators\GcToolkit.SourceGenerators.csproj"
                  OutputItemType="Analyzer" ReferenceOutputAssembly="false" />
<AdditionalFiles Include="Strings\**\Resources.resw" />   <!-- so the generator can validate name/tooltip keys -->
```

Notes: no `System.Text.Json` dependency (attribute-based, not JSON — so WinUI Gallery's `_GetDependencyTargetPaths` trick is unnecessary). Code generation uses `StringBuilder` + `AppendAutoGeneratedHeader` (**static `<auto-generated/>` header, no `DateTime.Now`** — the one improvement over WinUI Gallery, R13). New `PackageVersion` entries (`Microsoft.CodeAnalysis.CSharp`, `Microsoft.CodeAnalysis.Analyzers`, the generator-testing package) go in `src/Directory.Packages.props`.

## F. Generator testing contract

`tests/GcToolkit.SourceGenerators.Tests` uses the Roslyn source-generator testing harness (MSTest variant). Because discovery is **metadata-based**, tests must feed the attributed VMs in as a **referenced compilation** (a small in-memory `GcToolkit.Core`-like assembly defining `ToolAttribute`/`ToolViewModelBase`/the enums + sample `[Tool]` VMs), plus app-head view stubs and stub `.resw` `AdditionalFiles`. Minimum cases:
- **Happy path**: N attributed VMs (referenced) + view stubs → expected `GeneratedToolContributor` descriptors + `NavigationTree` (snapshot) + `AddDiscoveredTools` + `RegisterDiscoveredViews`.
- **`GCTOOL002`**: `[Tool]` on a non-`ToolViewModelBase` type → error.
- **`GCTOOL003`**: bad date → error.
- **`GCTOOL004`**: missing `<Id>_Tooltip` (stub `.resw` via `AdditionalFiles`) → error pointing at the resw.
- **Ordering/empty**: deterministic order; empty category/group omitted.
- **Determinism**: identical inputs → byte-identical output (no timestamp).
